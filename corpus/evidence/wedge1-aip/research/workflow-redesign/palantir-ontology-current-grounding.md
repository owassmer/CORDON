# Gate 5 — current Palantir Ontology grounding

**Status:** current official-platform grounding only; no CORDON Ontology design is proposed or accepted here  
**Retrieved:** 22 August 2026  
**Authority:** current Palantir Foundry documentation under [Ontology building](https://www.palantir.com/docs/foundry/ontology/), plus directly linked official Ontology, object/link, Action, Interface, Function, edit/history, migration, and permissioning pages.  
**Gate boundary:** this document distinguishes documented platform fact, Palantir design guidance, optional/developing capability, and later-gate implementation mechanics. Historical repository design, prior specifications, Foundry state, Challenge assumptions, and product surfaces are not premises.

## Executive verdict

Current documentation strongly validates Gate 5's sequence: model the real domain before source schemas; keep one focused object type per distinct real entity or event; make links express real named relationships; give a relationship its own backing object when the relationship carries facts; store each fact once; make Actions cohesive business operations; and add interfaces only for a demonstrated shared shape/capability. Palantir now publishes explicit, first-party Ontology design principles, structural guidance, and eight named anti-patterns, so Gate 5 should use those current pages rather than the older grounding's broader inferences ([best practices](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/), [structural guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/), [anti-patterns](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/)).

The refresh does **not** license CORDON design yet. In particular, it does not turn every accepted noun into an object type, every relationship family into one generic backing object, every event into an event object, every shared field into an interface, or every computation into a Function. Those decisions must be derived against the accepted Gate 1–4 grains.

## Coverage ledger

### Method and count

The complete 22-page `ontology/` subtree was recursively traversed from the official root. Every page in the directly linked `object-link-types/`, `action-types/`, `interfaces/`, `ontologies/`, `object-edits/`, `object-backend/`, and `object-permissioning/` subtrees was then traversed and scope-triaged. Eighteen Function pages directly relevant to Ontology reads, links, edits, interfaces, contracts, versioning, and migration were traversed; unrelated model, notification, external-call, and UI implementation pages were deliberately not expanded. Duplicate slash variants were canonicalized. **Total canonical pages traversed: 164.**

Disposition labels below mean:

- **Semantic:** directly informs Gate 5's concept or modeling choices.
- **Constraint:** changes what a semantically valid design can promise.
- **Optional:** documented but beta, enrollment-dependent, or not universally supported.
- **Deferred mechanics:** confirms feasibility/evolution but belongs to Gates 7–8 or implementation.
- **Scope-triaged:** traversed, but not used as a Gate 5 design premise.

## Concise current concept model

| Concept | Current documented platform fact | Gate 5 interpretation boundary |
|---|---|---|
| Ontology | The Ontology is an operational layer/digital twin over integrated assets. Its semantic elements include objects, properties, and links; kinetic elements include Actions, Functions, and dynamic security ([Ontology building](https://www.palantir.com/docs/foundry/ontology/), [core concepts](https://www.palantir.com/docs/foundry/ontology/core-concepts/)). | This says what Foundry can express. It does not require every Gate 5 design to contain every primitive or make an Ontology without an Action “incomplete.” |
| Object type / object / object set | An object type is the schema of a real-world entity **or event**; an object is one instance; an object set is a collection ([object types](https://www.palantir.com/docs/foundry/object-link-types/object-types-overview/)). | Admission still requires a meaningful, decision-relevant real grain. “Events are supported” is not “model every occurrence as an object.” |
| Property | A property is a characteristic of an entity/event. Required properties reject nulls during indexing and action apply, with a multi-datasource caveat; edit-only properties need no backing column but are OSv2-only ([properties](https://www.palantir.com/docs/foundry/object-link-types/properties-overview/), [required properties](https://www.palantir.com/docs/foundry/object-link-types/required-properties/), [edit-only](https://www.palantir.com/docs/foundry/object-link-types/edit-only-properties/)). | Gate 5 can name essential semantic characteristics and invariants. Backing columns, edit resolution, and storage mode are later implementation choices. |
| Shared property | Reuses and centrally manages property **metadata** across object types; underlying values are not shared ([shared properties](https://www.palantir.com/docs/foundry/object-link-types/shared-property-overview/)). | Repeated labels alone do not justify one; the same semantic property contract must actually recur. Shared property is not an Interface. |
| Value type | A space-scoped semantic wrapper over a primitive field type with reusable metadata/validation; unavailable in the Default ontology ([value types](https://www.palantir.com/docs/foundry/object-link-types/value-types-overview/)). | Optional typing mechanism, not a domain entity and not required for Gate 5. Enrollment/space and implementation decisions are deferred. |
| Struct | Groups one semantically related multi-field value, can carry metadata, and supports reducers; structs do not nest and fields cannot be arrays ([structural guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/), [properties](https://www.palantir.com/docs/foundry/object-link-types/properties-overview/)). | Use only for one value without independent identity, links, Actions, security, or lifecycle. Do not use a struct to hide a real noun or fact-bearing relationship. |
| Link type / link | A bidirectional link type defines one named real relationship with two independently named sides. Distinct relationships between the same endpoint types are distinct link types; cross-Ontology links are unsupported ([link types](https://www.palantir.com/docs/foundry/object-link-types/link-types-overview/)). | Do not create reverse duplicates or generic “related to” links. Gate 4's distinct predicates remain distinct even when endpoints match. |
| Direct vs. object-backed link | Direct links fit meaningful relationships with no relationship metadata. If the relationship owns dates, roles, status, allocation, or other facts, an intermediary object can back the link and expose those properties; object-backed links also support restricted views ([structural guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/#links-and-object-backed-link-types), [create link type](https://www.palantir.com/docs/foundry/object-link-types/create-link-type/#object-backed-links)). | This is the documented platform counterpart to Gate 4's independent fact-ownership test. It does **not** authorize seven generic relationship objects; each admitted predicate needs its real name and grain. |
| Cardinality | One-to-one, one-to-many, many-to-one, and many-to-many are modeled; one-to-one is an indicator of intent, not platform-enforced uniqueness ([create link type](https://www.palantir.com/docs/foundry/object-link-types/create-link-type/#choose-the-relationship-type)). | Gate 5 must state real-world cardinality and separately flag any uniqueness invariant that cannot rely on the 1:1 label. Storage mapping is deferred. |
| Action type | An Action is one transaction that applies a cohesive set of object/property/link edits and side effects. Rules can create, modify, delete, and link objects; submission criteria independently govern whether the Action may be submitted ([Actions](https://www.palantir.com/docs/foundry/action-types/overview/), [rules](https://www.palantir.com/docs/foundry/action-types/rules/), [criteria](https://www.palantir.com/docs/foundry/action-types/submission-criteria/)). | Derive verbs from accepted decision rights and bounded operations—not CRUD forms, status setters, or an implementation wish list. Exact parameters, criteria syntax, side effects, permissions, and scale are deferred. |
| Function | A Function is server-side code for fast operational logic; it can read objects, properties, links, and object sets. Ontology edit Functions only persist through a function-backed Action ([Functions](https://www.palantir.com/docs/foundry/functions/overview/), [Functions on objects](https://www.palantir.com/docs/foundry/functions/functions-on-objects/), [edits](https://www.palantir.com/docs/foundry/functions/edits-overview/)). | Gate 5 should name a Function only when live, cross-object, or otherwise complex logic cannot be represented as stored truth, derived property, or simple Action rule. Code language and repository mechanics are deferred. |
| Interface | An Interface is abstract, datasource-free, non-instantiable, and implemented by concrete object types. It can declare properties, link constraints, and beta action-type constraints; interfaces and object types can compose through multiple extension/implementation ([Interfaces](https://www.palantir.com/docs/foundry/interfaces/interface-overview/)). | Admit only a proven shared semantic/capability contract used polymorphically. Do not use an Interface merely because Natural Person and Organization share a display name, or as a substitute for a generic superclass object. |
| History | Current state, Action decision logs, user-edit history, linked domain history/amendment objects, time-series values, and branch/proposal history are different mechanisms ([anti-patterns](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/#anti-pattern-the-time-machine), [Action log](https://www.palantir.com/docs/foundry/action-types/action-log/), [edit history](https://www.palantir.com/docs/foundry/object-edits/user-edit-history/)). | Gate 5 must preserve consequential domain history without copied entity versions or a generic global timeline. Platform audit/log objects do not automatically become core domain objects. |
| Lifecycle/evolution | Resources start `experimental`; `active` resources cannot be deleted or have API names changed; `deprecated` resources record reason/deadline/replacement; object types may be `promoted`. OSv2 supports guided migrations for many breaking edited-schema changes ([statuses](https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses/), [schema migrations](https://www.palantir.com/docs/foundry/object-edits/schema-migrations/)). | Names, identity, and semantic boundaries deserve early care, but the platform supports iterative evolution. Status, branching, and migration plans belong to implementation. |
| Ontology boundary | One Ontology maps 1:1 to one space; private and shared Ontologies differ by organization scope; links cannot cross Ontologies ([Ontologies](https://www.palantir.com/docs/foundry/ontologies/ontologies-overview/), [shared Ontologies](https://www.palantir.com/docs/foundry/ontologies/shared-ontologies/)). | This may constrain later deployment topology, but Gate 5 must not choose spaces or organization sharing architecture. |

## Documented best practices Gate 5 should apply

1. **Model reality, not source systems.** Identify entities before examining schemas; model the domain, then map data. Links represent real relationships, not foreign-key artifacts ([best practices](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/#1-domain-driven-design)).
2. **Separate identity from observation—but treat this as a test, not an automatic type rule.** Palantir says that when a row is a measurement/event about an entity, entity and observation are *likely* different types. Gate 5 must still establish an independently meaningful event/observation grain ([best practices](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/#best-practices)).
3. **One focused type per distinct real entity/event.** Avoid both source/department copies and a sparse “God Object.” A minimum type count is not the objective; minimum semantic duplication and maximum clarity are ([anti-patterns](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/)).
4. **Store each fact once.** Use runtime derived properties when a value depends on links or Ontology edits; pre-compute stable same-object transformations upstream. At query scales above roughly 10,000 objects, selective denormalization may be a documented performance tradeoff, not the default ([structural guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/#normalization-and-derived-properties)).
5. **Use semantically meaningful links.** One link is already bidirectional. Create multiple links between the same endpoint types only for genuinely different predicates; name each side so traversal reads naturally ([link types](https://www.palantir.com/docs/foundry/object-link-types/link-types-overview/#directionality)).
6. **Put relationship facts on the relationship.** When dates, role, allocation, status, scope, or comparable metadata belongs to the relationship rather than either endpoint, use an object-backed link and preserve the detailed intermediary even if some workflows expose a direct view ([structural guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/#links-and-object-backed-link-types)).
7. **Name for domain users and agents.** Use singular concrete object nouns, qualified properties, and explicit relationship names; avoid `Item`, `Record`, `value`, `type`, `date`, and `relatedItems` ([naming guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/#naming-conventions)).
8. **Use cohesive Actions for business operations.** Bundle the edits that comprise one real operation, name the verb after that operation, and use submission criteria for decision-time rules. Do not model Action inventory as one setter per field ([Action Sprawl](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/#anti-pattern-action-sprawl), [submission criteria](https://www.palantir.com/docs/foundry/action-types/submission-criteria/)).
9. **Choose the right semantic/tool boundary.** The current anti-pattern page assigns human or agentic decisions to Actions, automated transformations to pipelines, event reactions to Automations, and complex live cross-object logic to Functions. Gate 5 may use this only to avoid inventing Functions/Actions for the wrong kind of responsibility; pipelines and Automations themselves remain later-gate topics ([Golden Hammer](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/#anti-pattern-the-golden-hammer)).
10. **Use Interfaces for actual reusable contracts.** Current guidance favors capability or taxonomic interfaces, multiple composition, and workflows targeting interfaces where supported. The rule-of-three is a practical refactoring signal—not a mandatory threshold for every valid Interface ([best practices](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/#2-do-not-repeat-yourself-rule-of-three), [Interfaces](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/#interfaces)).
11. **Protect core semantics and extend deliberately.** Once field-tested, core types should be stable; extensions can use linked types, new interface implementations, or new property namespaces. Critical invariants are naming, semantic clarity, and security—not premature perfection ([open/closed guidance](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/#3-open-for-extension-closed-for-modification), [tradeoffs](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/#pragmatism-and-tradeoffs)).
12. **Keep security aligned with the domain without duplicating semantic types.** Row and column controls should follow domain boundaries. Do not create separate public/private copies of one real entity; do not scatter access filtering through applications ([security design](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/#security-design)). Gate 5 records only whether a proposed split is falsely security-driven.
13. **Model current identity once; choose history mechanism by purpose.** The Time Machine anti-pattern rejects copied entity versions. Use current properties plus real linked amendment/history entities, time-series properties, edit history, or Action logs according to the history question ([Time Machine](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/#anti-pattern-the-time-machine)).
14. **Document semantic decisions.** Object types, properties, and links need descriptions, and names should be reviewed with domain users ([design guidelines](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/#design-guidelines)).

## Current documented anti-patterns and Gate 5 tests

| Palantir anti-pattern | Current documented meaning | Gate 5 rejection test |
|---|---|---|
| System Silos | One type per source for the same real entity | Reject any candidate whose identity is a file, table, portal, register, or source system rather than the accepted real noun. |
| Kitchen Sink | Expose technical/ETL columns “just in case” | Admit only properties used to identify, distinguish, decide, act, explain, secure, or preserve a required fact. Keep ingestion metadata backstage. |
| Department Silos | Duplicate shared entities by team/department | The five operating responsibilities cannot create five versions of a member, Holding, Parcel, Proceeding, or Intervention. |
| God Object | One sparse type represents many different entities | Do not collapse the 13 nouns merely to minimize types; do not create a generic Actor, Asset, Case, Item, or Work object whose fields change meaning by subtype. |
| Golden Hammer | Use Actions, pipelines, Functions, etc. for work suited to another capability | Reject a Function that only concatenates stable fields; reject an Action that merely triggers a calculation; reject platform mechanics as semantic nouns. |
| Action Sprawl | One narrow Action per property edit | Every candidate Action must name one accepted real operation/decision and the bounded changes it owns. |
| Time Machine | Copy one entity into multiple version objects/types | Preserve one persistent identity. Add only real amendments, operative instruments, proceedings, or bounded outcomes when they have their own grain; do not make snapshot copies or yearly types. |
| Misnomer | Vague/generic names hide meaning | Reject `Case`, `Status`, `Event`, `Evidence`, `Assignment`, `Effect`, `Scope`, or `relatedTo` unless the name is qualified to the real predicate/grain and survives domain review. |

Official source for all eight: [Ontology design: Anti-patterns](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/).

## Optional and developing capabilities that must not become assumptions

- **Derived properties are Beta** and may be enrollment-unavailable. They are runtime values usable in TypeScript OSDK `withProperties`; they currently exclude OSv1 queries, text/keyword search, some struct-bearing OSDK queries, and Marketplace Function packaging. They inherit the security of every contributing object ([derived properties](https://www.palantir.com/docs/foundry/ontology/derived-properties/)). Gate 5 may identify a derivation semantically but cannot assume a derived-property implementation.
- **Interface action type constraints are Beta.** They constrain user-facing meaning, API name, and parameter shape, but do not define or enforce concrete logic, submission criteria, side effects, or layout. They are not currently invocable/discoverable from Foundry applications or OSDK ([interface action constraints](https://www.palantir.com/docs/foundry/interfaces/interface-action-type-constraints/)).
- **Interface support remains uneven.** TypeScript v2 Functions support interfaces; Actions and Object Set Service are partial; TypeScript OSDK is supported while Java/Python are in development; Workshop, TypeScript v1 Functions, and Python Functions do not support them ([Interface support](https://www.palantir.com/docs/foundry/interfaces/interface-overview/#current-levels-of-support)). Therefore Gate 5 may define a justified Interface contract but must not make a later surface depend on unsupported behavior.
- **Value types are optional and space-scoped**, not Ontology resources, and unavailable in the Default ontology ([value types](https://www.palantir.com/docs/foundry/object-link-types/value-types-overview/)).
- **Required, edit-only, mandatory-control properties, and Action reverts are OSv2-dependent** ([required properties](https://www.palantir.com/docs/foundry/object-link-types/required-properties/), [edit-only properties](https://www.palantir.com/docs/foundry/object-link-types/edit-only-properties/), [mandatory controls](https://www.palantir.com/docs/foundry/object-link-types/mandatory-control-properties/), [Action reverts](https://www.palantir.com/docs/foundry/action-types/action-reverts/)). These are feasibility notes, not Gate 5 representation premises.
- **One-to-one is not uniqueness enforcement.** Any Gate 5 uniqueness invariant needs later validation/enforcement design ([link creation](https://www.palantir.com/docs/foundry/object-link-types/create-link-type/#choose-the-relationship-type)).

## Consequences and questions Gate 5 must apply

These are design tests, not answers for CORDON.

### Object admission

1. Which accepted nouns need persistent object identity in the operator's decisions, and which can remain a value, classification, derived object set, or contextual role?
2. For each admitted object, is the instance one real entity/event—not one source row, department view, workflow lane, snapshot, or generic container?
3. Does an event/outcome candidate have its own independently referable grain and facts, or can the bounded consequence be represented on a surviving noun/relationship plus Action/edit history? Platform support for events does not answer this domain question.
4. Are Natural Person and Organization genuinely separate concrete types while any shared contract remains an Interface question rather than a forced common object superclass?
5. Would any “minimal” consolidation become a God Object with sparse properties or subtype-conditioned meanings?

### Property and identity tests

6. Which properties are essential semantic characteristics or invariants? Which are source/ETL metadata, cached linked values, status conveniences, or implementation timestamps that should be excluded?
7. Is each fact stored once at its semantic owner? If a convenience value is derived, what are its source facts and does Gate 5 merely specify the derivation rather than assume Beta runtime support?
8. Does any grouped multi-field value truly behave as one struct value, or does it need independent identity, links, Actions, security, or lifecycle?
9. What is the stable real-world identity rule for every object and relationship-fact object? Gate 5 should define identity semantics, not physical key type or source-column mapping.
10. Which invariants are semantic requirements even though current 1:1 cardinality metadata will not enforce them?

### Relationship tests

11. For every one of the 16 accepted atomic anti-collapse predicates, what is the exact named predicate in both traversal directions?
12. Does the relationship own effective dates, basis, scope, role, amount, allocation, authority, status, accepted quantity, or another independent fact? If yes, test a distinct object-backed relationship representation; if no, retain a direct link.
13. Are different predicates between the same endpoints preserved as different links rather than collapsed into a generic relationship type?
14. Does any proposed direct link incorrectly infer a relationship transitively or promote geometry/source joins into domain fact?
15. Does an object-backed relationship remain visible under its real domain noun/predicate rather than a generic `Assignment`, `Effect`, `Scope`, or family name?

### Action and Function tests

16. What exact real decision or operation does each candidate Action represent, who owns it, what bounded edits occur atomically, and what must remain outside it?
17. Is an Action cohesive, or is it a field setter, generic state transition, or several independent decisions collapsed together?
18. Which refusal conditions follow from accepted decision rights? Gate 5 can state semantic conditions and failure consequences; parameter paths, group IDs, permissions, and criteria syntax are deferred.
19. Does a proposed Function require live cross-object computation, traversal, or complex edit logic? If it is stable ingestion-time transformation, simple aggregation, or stored truth, do not admit it as a core Function.
20. If a Function edits the Ontology, is its semantic contract explicitly behind an Action? The documented platform does not persist edit-function results by direct invocation ([edit Functions](https://www.palantir.com/docs/foundry/functions/edits-overview/#when-edits-are-applied)).
21. Are generated Action Logs/edit histories being mistaken for operator-domain nouns? They are optional audit mechanisms and later implementation resources.

### Interface and evolution tests

22. What concrete types share the same semantic shape or capability, and what real workflow benefits from operating polymorphically across them?
23. Is the Interface narrow and composable, or a disguised deep hierarchy/generic supertype? Are required properties, links, and Actions truly universal?
24. Would an optional Interface element support incremental adoption without blocking existing implementations? Current action constraints are beta and do not enforce behavior.
25. Which API/display names and semantic boundaries are hard to change after activation and therefore need domain-user review now? Which implementation details can remain experimental and evolve through branches/migrations?
26. Does a proposed type split exist only for security? If so, reject it and defer row/column/domain-policy implementation rather than duplicating the semantic model.

The comparison below uses the older grounding only as a claims checklist; none of it is a design premise.

| Earlier claim | Current correction / supersession |
|---|---|
| “The Ontology is a decision system… A semantic catalog without operational actions is incomplete.” | Current docs call the Ontology an operational layer/digital twin containing semantic **and** kinetic elements, but do not state that every valid Ontology or Gate 5 core must include every element. Gate 5 should derive only Actions/Functions required by accepted decisions ([Ontology building](https://www.palantir.com/docs/foundry/ontology/)). |
| “Separate identity from observation” as a binding rule | Current best practices say that if a row represents a measurement/event about an entity, they are **likely** different object types. This is a diagnostic, not automatic admission of Observation, Assessment, Result, or Event objects ([best practices](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/#best-practices)). |

Gate 4's independent fact-ownership test remains controlling ([structural guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/#links-and-object-backed-link-types)). |
| “Action Logs are decision objects.” | Current docs say Action logs are generated object types designed to capture Action decisions: one log type per enabled Action, one object per submission, linked to edited objects. That is an **optional platform audit representation**, not proof that every decision/event belongs in the core domain Ontology ([Action log](https://www.palantir.com/docs/foundry/action-types/action-log/)). |
| “Strings are the safe default” for primary keys | Current property docs list String, Integer, and Short as valid common primary-key types; Date/Timestamp and Boolean/Byte/Long are discouraged for stated reasons, while float-like types are invalid. | “Interfaces can define properties and link/action constraints,” without qualification | Still broadly true, but current docs sharpen the boundary: action constraints are Beta, describe shape rather than behavior, cannot be invoked/discovered by end users or OSDK, and must map to concrete Actions whose logic/criteria remain independently reviewed ([interface action constraints](https://www.palantir.com/docs/foundry/interfaces/interface-action-type-constraints/)). |
| “Source-backed and operator-authored state are distinct” as a design implication | This is an implementation mechanism, not a semantic split. OSv2 can combine datasource values and Action edits under explicit conflict-resolution strategies; edit-only properties always apply. Gate 5 must model the real fact and authority, not create separate semantic types because storage paths differ ([how edits apply](https://www.palantir.com/docs/foundry/object-edits/how-edits-applied/)). |
| Application/tool selection claims (Object Views, Workshop, OSDK, etc.) | Those belong to Gates 7–8. The current Interface support matrix is relevant only as a non-assumption; it does not select a CORDON surface ([Interface support](https://www.palantir.com/docs/foundry/interfaces/interface-overview/#current-levels-of-support)). |
| Media-generation and Function language claims | These are later capability/implementation details and have no authority over Gate 5's semantic model. They are explicitly deferred. |
| Security should align to “portfolio, authority, and purpose” | Current official guidance says security should follow **domain boundaries**, use least privilege, combine row/column controls, and avoid duplicate types for security. The prior project-specific examples were not platform doctrine ([security design](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/#security-design)). |
| History can be solved generically by linked changes/history | Current docs present several distinct choices: a real linked amendment/history object, time-series property, user-edit history, Action log, and branch/proposal history. Gate 5 must choose by the real-world history question and must not create copied entity versions or one global timeline ([Time Machine](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/#anti-pattern-the-time-machine), [edit history](https://www.palantir.com/docs/foundry/object-edits/user-edit-history/)). |

## Explicitly deferred beyond Gate 5

1. **Broad Foundry/AIP capability mapping:** pipelines, streaming, Automations, models, AIP, semantic search, document processing, media, schedules, notifications, webhooks, external calls, and full tool selection belong to Gate 6.
2. **Operator surfaces:** Workshop, Object Views, Object Explorer, Quiver, Map, OSDK/custom applications, navigation, forms, tables, and UI composition belong to Gate 7.
3. **Physical data design:** backing datasets, virtual tables, joins, source precedence, source-to-property mappings, transforms, indexing, materializations, writeback, and data cleaning.
4. **Storage implementation:** OSv2 migration, Funnel behavior, edit conflict strategy, schema-migration instructions, edit-history retention, performance thresholds, and backend compatibility.
5. **Security architecture:** spaces/organizations, private vs. shared Ontology deployment, markings, restricted views, mandatory controls, row/column policies, grants, groups, tokens, and approval policies. Gate 5 only prevents security-driven semantic duplication and notes any domain boundary a later design must respect.
6. **Action implementation:** parameter types/order, overrides, submission-criteria syntax, group IDs, side effects, Action logs, reverts, branch behavior, permissions, batching, and scale tuning.
7. **Function implementation:** TypeScript/Python/version choice, repositories, OSDK generation, imports, edit batches/staged writes, version tags, deployment, tests, runtime limits, and optimization.
8. **Ontology operations:** API names as finalized implementation identifiers, statuses, promotion, branching, proposals, resource protection, migrations between Ontologies, and release/change-management process.
9. **Optional capability commitments:** derived properties, value types, structs/reducers, Interface action constraints, Interface-backed workflows, or any beta/enrollment-dependent feature. Gate 5 may state a semantic need and alternatives, but may not assume deployment support.
10. **CORDON design itself:** this file does not choose object types, relationship objects, direct links, properties, cardinalities, Actions, Functions, Interfaces, primary keys, or names. It supplies the current documentation tests that the next Gate 5 derivation must apply.

## Gate 5 grounding conclusion

The current official documentation is materially more explicit than the earlier grounding: Palantir now publishes a prioritized design doctrine, structural guidance, and a named anti-pattern catalog. The binding takeaway is not “use more Ontology features.” It is: **preserve real identity and predicate grain, curate ruthlessly, store each fact once, make relationships and operations semantically explicit, and introduce abstraction only after a real shared contract appears.** Optional or storage-specific mechanisms must remain alternatives until later gates establish enrollment support and implementation need.
