# Gate 5 deletion-first object and event admission

**Status:** PRE-CORRECTION OBJECT/EVENT UPPER BOUND — software admission reopened
**Date:** 22 August 2026  
**Authority:** `REDESIGN_SEQUENCE.md`; `connected-operating-model.md`; accepted Gate 3–4 authorities and Gate 5 reconciliation/verification; current official Palantir Ontology guidance  

## Verdict

The deletion-first test admits **12 unconditional real-world object types and one conditional object type** from the 13 accepted nouns. `Individual Plant` is conditional on real identity being preserved by an authority, registry, field process, operative instrument, or validated reproducible observation-derived inventory. It is not created from an arbitrary detection or coordinate.

The test also identifies **six concrete event-object candidates** whose occurrence identity is consequential and is not safely replaced by current endpoint state, a relationship fact, or a generic audit trail:

1. Official Notice or Service;
2. Public Filing Submission;
3. Plant Material Movement;
4. Field Execution Occurrence;
5. Field Inspection or Acceptance Occurrence;
6. Cash Settlement Transaction.

Each is a specifically named domain occurrence, not a subtype of a generic `Event`. Admission is at the real external grain only. Where the governing process does not preserve the stated occurrence identity and facts, the occurrence remains an Action, an edit, a fact on a surviving object/relationship, or platform history rather than an object.

All other tested events and outcomes are rejected as object types at this gate. Their consequences belong once on the surviving noun, the exact fact-bearing relationship, a newly created `Governing Instrument` or `Public Proceeding` where that real noun is produced, and/or the cohesive Action and its optional platform history. This does not erase history: it rejects duplicate domain identity where no independent occurrence must be referred to.

## Test and documentation basis

For every candidate, ask in order:

1. **Real identity:** Does one instance exist independently of CORDON, a source row, a screen, a responsibility lane, or a platform log?
2. **Operator decision:** Which accepted decision becomes unsafe or impossible unless operators can refer to that same instance after correction, handoff, amendment, delay, or reopening?
3. **Deletion consequence:** If the candidate object type were deleted while surviving nouns, exact relationship facts, cohesive Actions, and available history remained, what decision-relevant capability would be lost?
4. **Single owner:** Can the needed fact instead live once on a surviving noun or exact fact-bearing relationship, or be preserved as the creation/modification of another admitted noun?
5. **Concrete grain:** For an event, is it a named domain occurrence with independently referable facts rather than a generic Event, status, observation, source record, or Action Log?

Current official Palantir guidance supplies the representation boundary:

- An object type is the schema of a real-world **entity or event**, and one object corresponds to one real entity or event: [Object types](https://www.palantir.com/docs/foundry/object-link-types/object-types-overview/).
- Model reality rather than systems, keep object types focused, and separate identity from an observation/event only when the grains are genuinely different: [Ontology design — Best practices](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/).
- Store each fact once; use direct links when a relationship has no metadata and an object-backed link when the relationship owns dates, roles, status, allocation, or comparable facts: [Ontology design — Structural guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance/).
- Avoid source and department copies, God Objects, one-field Actions, copied entity versions, and vague nouns: [Ontology design — Anti-patterns](https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/).
- An Action is one transaction that makes a cohesive set of object/property/link edits; it captures an operation without requiring a separate domain-event object: [Action types](https://www.palantir.com/docs/foundry/action-types/overview/).
- An optional Action Log creates one platform log object per Action submission and edit history can preserve object edits. Neither mechanism proves that the submitted operation is itself a core domain noun: [Action log](https://www.palantir.com/docs/foundry/action-types/action-log/), [User edit history](https://www.palantir.com/docs/foundry/object-edits/user-edit-history/).

`Docs basis` below abbreviates these current pages as **OT** (Object types), **BP** (Best practices), **SG** (Structural guidance), **AP** (Anti-patterns), **AT** (Action types), **AL** (Action log), and **EH** (edit history).

### Noun alternatives that are not object types

- `Natural Person` and `Organization` may later implement a narrow shared Interface only if a proven polymorphic actor workflow requires universal properties/links/actions. An Interface is abstract and cannot replace either concrete object identity. No such Interface is admitted by this test alone.
- Member, beneficiary, owner, holder, applicant, cooperative, authority, CAA, contractor, nursery, inspector, executor, creditor, payee, guarantor, successor, and representative are contextual roles/classifications or F1/F7/F9 relationship facts, not object types or permanent endpoint subtypes.
- Route family, readiness, eligibility, selected/blocked/accepted/paid/complete, firmness, outcome kind, effect kind, proceeding kind, taxonomic rank, cultivar category, and similar controlled terms are values/classifications. They do not have independent identity merely because they need controlled vocabulary.
- Feasible portfolios, expected-loss scores, affected-work sets, cohorts, overlays, and current-route summaries are derived sets/results unless a real governing process later gives one independent identity and lifecycle.
- A shared field or label is not an Interface. Current guidance requires a useful shared shape or capability, not superficial resemblance.

## C. Why the six event-object candidates survive deletion

| Candidate | Required independently referable grain | Facts it alone owns | What it must not absorb |
|---|---|---|---|
| Official Notice or Service | One legally consequential publication/service occurrence recognized by the controlling process. | Notice/service identity, issuing actor, recipient or published scope, channel, effective time, proof, linked Instrument/Proceeding, clock triggered. | The rule/instruction itself (`Governing Instrument`), recipient identity, generic communications, source captures, or all clock state. |
| Public Filing Submission | One externally released and received protocolled submission/version in one Public Proceeding. | Filing/protocol identity, submission kind, filer, receiving authority, time, exact submitted version/scope, receipt, superseded/corrected submission relation. | The enduring `Public Proceeding`, a dossier, all evidence, eligibility/concession outcome, or draft preparation. |
| Plant Material Movement | One governed movement/handoff occurrence for one or more traceable Lots. | Movement identity, origin/destination actors/places as applicable, Lots and quantities, dispatch/receipt times, conditions, acceptance/rejection/return link. | Persistent custody/allocation (F9), stock commitment (F6), Intervention use (F5), or passport/source artifacts. |
| Field Execution Occurrence | One bounded occasion of physical work performed within an Intervention. | Execution identity, kind, executor, time, actual work scope/material/quantity, method, exceptions, linked work authority, later inspected occurrence. | The persistent `Intervention`, intended/authorized scope (F5), generic evidence, or acceptance conclusion. |
| Field Inspection or Acceptance Occurrence | One authority-/contract-/protocol-recognized review occasion, including bounded establishment/defect review. | Inspection/verbale identity, competent actor, time, inspected execution/scope, observations, admissible/accepted/rejected quantities, decision, defects, follow-up. | A generic Inspection superclass, the `Public Proceeding`, all statuses, or biological/productive maturity beyond Wedge 1. |

These are candidates for concrete object types because deleting any one of their occurrence grains while retaining current endpoint state would erase a required answer to “what changed,” “what was done,” “who accepted it,” or “did the intended result land.” The exact local split/merge and identity rules remain contingent on grain-sufficient real process evidence; no source schema or existing Foundry state is a premise.

## E. Admission rules carried forward

1. **No generic ancestors.** The six event candidates stand alone. Do not create `Event`, `Case`, `Evidence`, `Status`, `Observation`, `Decision`, `Outcome`, `Source`, `Task`, `Queue`, `WorkItem`, dossier, bundle, or timeline objects.
2. **No source identity.** A protocol number, bank reference, verbale number, or shipment identifier may establish the real occurrence identity; the PDF, file, portal record, message, receipt image, or source row is not the object.
3. **No duplicate consequence.** Creation/modification of a Governing Instrument, Public Proceeding, F1–F9 relationship, Intervention, or other admitted noun is not accompanied by a parallel event object unless the concrete occurrence independently survives the deletion test.
4. **No status objects.** Outcome kind, firmness, readiness, admitted/refused, accepted/rejected, paid/returned, surviving/failed, open/closed, and similar terms are scoped properties/classifications or derivations at their semantic owner.
5. **No automatic observation objects.** A measurement or finding becomes a concrete event object only when operators must refer to that same occurrence independently. Otherwise it is a value/struct on E23 or another semantic owner, with backstage provenance as needed.
6. **No Action Log substitution.** Action Logs and edit history are optional platform audit mechanisms. They can preserve CORDON submissions/edits but cannot substitute for externally recognized notice, filing, movement, execution, inspection, or bank-transaction identity.
7. **No event-object inflation.** A real external identifier is necessary evidence of grain but is not sufficient admission. The occurrence must also own decision-relevant facts and survive deletion against nouns, F1–F9 facts, and available history.
8. **Selective reopening.** If direct evidence shows that a currently rejected event—such as a laboratory occurrence or dispatch—has independently recognized identity and is repeatedly referenced by accepted decisions, reopen only that row and rerun the same test.
