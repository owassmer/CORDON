### 2.7 The Fasano trap — a second date error waiting in the same regulation

**Fasano does not enter Annex III on 2024-06-05. Fasano has been inside Annex III Part A since 2020-08-20.**

The reasoning, entirely from §1.5, §1.6 and §1.11:

1. Part A point 2 has read "The province of Brindisi" — the whole province, unqualified — since 2020-08-20, and `▼B` markers in the consolidated text confirm it has never been amended.
2. ISTAT places Fasano in the province of Brindisi, comune code 074007, province code 074.
3. Therefore Fasano fell inside Part A point 2 from 2020-08-20.
4. Regulation 2024/1320 inserts "Fasano" into point 3, the **Taranto** list, and its recital (2) calls Fasano "the municipality of Fasano in the province of Taranto".

The regulation mis-provinces Fasano. Recital (2) and the Annex instruction agree with each other and both disagree with ISTAT. The insertion is legally effective — the enacted text says what it says — but it is **membership-neutral**: Fasano was already in Part A via point 2, so its Annex III status does not change on 2024-06-05.

Consequence for the build: an engine that derives entry dates by diffing the enacted lists will report `Fasano: entered 2024-06-05`. That is wrong by 1,385 days. It will also report Fasano's province as Taranto, which will fail any join against an ISTAT comune roster keyed on province 074.

Structurally this is the same failure as the TAR Bari 17.05.2024 trap flagged in the task, and it is worth naming the shared shape: **a derived date beats a stated one only when the stating instrument is authoritative for that fact.** A judgment is authoritative about its holding, not about another act's commencement. A regulation is authoritative about its own enacted text, not about Italian administrative geography. Take commencement from the act's final Article; take province assignment from ISTAT.

Recommended handling: record Fasano's Part A membership as beginning 2020-08-20 with basis `province:Brindisi`, and record the 2024/1320 point-3 insertion as a separate, membership-neutral listing event carrying an explicit anomaly flag. Do not let the point-3 listing set Fasano's province.

Three independent checks, all from §1.12 and the fetch log:

1. The base act's EUR-Lex page, fetched 2026-08-19, states the current consolidated version is 24/11/2025. EUR-Lex advances that pointer when a new consolidation is produced.

### 2.9 The model, for the builder

**LegalAct rows: 8.** Seven acts plus one corrigendum. The consolidated text is **not** a LegalAct — it is a documentation rendering with no legal effect, and the current single-row defect is exactly what happens when it is treated as one. Register it, if at all, as a `SourceDocument` used for cross-checking.

Each LegalAct row carries:

| Field | Note |
|---|---|
| `celex` | primary key: `32020R1201`, `32021R1688`, `32021R2130`, `32023R1706`, `32024R1320`, `32024R2507`, `32025R2231`, `32020R1201R(01)` |
| `act_number` | e.g. `(EU) 2024/1320` |
| `title` | full OJ title |
| `done_at_date` | "Done at Brussels" date from the act's signature block |
| `oj_publication_date` | OJ date |
| `oj_reference` | e.g. `OJ L 269, 17.8.2020, p. 2` / `OJ L, 2024/1320, 16.5.2024` |

**AnnexIIIEntry rows: the membership table.** One row per territorial entry per validity interval. Critically, entries are at **two different scope levels** — points 1 and 2 name whole provinces, points 3 and 4 name comuni — and a flat comune list cannot represent that without silently baking in a province roster snapshot.

| Field | Note |
|---|---|
| `annex_part` | `A` / `B` / `C` / `D` |
| `point_no` | `1`–`4` for Part A |
| `scope_level` | `province` or `comune` |
| `territory_code` | ISTAT province code (`075` Lecce, `074` Brindisi, `073` Taranto, `072` Bari) or ISTAT comune code |
| `territory_name_as_enacted` | the string as printed in the OJ |
| `valid_from`, `valid_to` | `valid_from` = EIF of the introducing act; `valid_to` null while in force |
| `introduced_by_celex`, `removed_by_celex` | |
| `province_as_enacted` | for the Fasano anomaly: `Taranto` as enacted vs `074`/Brindisi per ISTAT |
| `anomaly_flag` | set on the Fasano point-3 listing |

Part A needs 30 rows: 2 province rows + 22 Taranto comuni + Locorotondo, all `valid_from` 2020-08-20; then Fasano (point 3, `valid_from` 2024-06-05, anomaly-flagged, membership-neutral) and the 5 new Bari comuni `valid_from` 2024-06-05.

**Resolving "Annex III membership for comune C as of date D":**

```
SELECT 1 FROM annex_iii_entry e
JOIN comune c ON c.istat_code = :C
WHERE e.annex_part = 'A'
  AND e.valid_from <= :D
  AND (e.valid_to IS NULL OR :D < e.valid_to)
  AND (
        (e.scope_level = 'comune'   AND e.territory_code = c.istat_code)
     OR (e.scope_level = 'province' AND e.territory_code = c.province_code_at(:D))
      )
```

Three properties this buys, each answering a way the current single-row model fails:

- **As-of correctness.** The interval predicate is the whole point. `2024-03-15` selects A/1 and returns false for Monopoli; `2024-07-01` selects A/2 and returns true.
- **Province expansion stays honest.** Point 2 is not flattened into 20 comune rows at load time. It resolves through `comune.province_code_at(:D)`, so a comune that changes province between D and today does not silently change its historical Annex III status.
- **Provenance survives.** Every true answer traces to a CELEX, an entry-into-force date, and a hashed PDF.

`valid_to` is exclusive: A/1's interval is `[2020-08-20, 2024-06-05)`, so 2024-06-04 is the last day of A/1 and 2024-06-05 is the first day of A/2. Fixing the convention matters — an inclusive/exclusive mix-up reproduces exactly the one-day class of error this brief exists to prevent.

### 2.10 Adjacent finding, outside the Annex III question

2024/2507 replaces Article 15(2)(a). The area of the infected zone subject to annual containment surveys drops from "at least 5 km" to "at least 2 km" from the buffer-zone border, effective 2024-10-17. This changes what containment *requires* inside an Annex III zone without changing the zone's membership. Flagging it because a containment-obligations model will need its own as-of interval; it is out of scope here.

## GAPS

- **G-1. Province rosters not acquired.** Part A points 1 and 2 admit whole provinces, so answering membership for a Lecce or Brindisi comune requires an ISTAT comune roster for province `075` and `074`. The Brindisi roster (20 comuni) is captured at §1.11 from ISTAT 8milaCensus, but that page is a 2011-census rendering — it is a starting point, not a dated authority. **No Lecce roster was fetched.** Both rosters must be acquired from ISTAT SITUAS with validity dates, because comune counts change: ISTAT's own classification page notes Italy dropped to 7,894 comuni on 2026-02-21 through a merger. A province roster is itself a temporal object.
- **G-2. Hash volatility.** EUR-Lex generates these PDFs on demand. The §1.13 hashes fix the retrieved artifacts and may not reproduce on re-fetch. If the build needs stable content hashing, hash the extracted text rather than the PDF container, or archive the retrieved bytes.
